Persona hypotheses, inferred from the SRS and task rather than observed participants:

1. **First-use macOS developer:** open Dashboard after a managed command. Existing newest-job selection exposes the outcome and inline measurements without another navigation action. If another job is intended, select its Recent row once. Read CPU used, Run elapsed, Queue wait and scope; open Accounting details only for precision or attribution.
2. **Repeat diagnosis:** select a queued, exit-17 or signaled job. Read outcome independently from measurement quality; distinguish queue delay from run duration. If tracking is unavailable, use existing Refresh status / Retry connection, retaining the same job and last valid summary. Recovery performs reads only and never offers or initiates another execution.
3. **Keyboard user:** Tab to Recent, move focus with arrows/Home/End, select with Enter/Space, then Tab to Accounting details and toggle with Enter/Space. Focus remains on the selected row after selection; polling does not move it. Read the visible Partial reason without opening anything.

This is the required additive interface, not a command executed in this design task. Retain by-ID selection even when it falls outside the next 50-record page.

## Measurement and copy contract

Use a `Job measurements` subsection within Selected job. Preserve the outcome and recorded-state help above it. Show the following rows in reading order in the existing single-column / `sm` two-column definition-list pattern. Keep the scope and quality explanation full-width. No nested card, extra destination, setup step or utilization chart is required.

| Visible label | Value / help | Meaning and unavailable behavior |
| --- | --- | --- |
| **CPU used** | `{value} core·s`; help: `Cumulative user + system CPU for the recorded scope.` | Sum of recorded user and system CPU work in core-seconds. Parallel work can exceed Run elapsed. Do not normalize by host core count or display a percent, capacity gauge, dollar saving or estimated token charge. Show `Unknown` if no valid total exists; never sum incomplete components into a claimed total. |
| **Run elapsed** | `{value} s`; help: `Monotonic elapsed time from native spawn through terminal observation. Includes stopped time.` | Includes SIGSTOP → SIGCONT time; excludes queueing and post-termination reporting. Display the captured interval, independently of lifecycle receipt timestamps. Do not calculate it by subtracting displayed wall times or extrapolate a live value. |
| **Queue wait** | `{value} s`; help: `Recorded time from queue entry to reservation.` | Separate scheduler interval with its supplied clock/basis. A verified new lifecycle-only execution with no scheduler queue may show `0 s · No scheduler queue used`. Missing queue evidence, legacy data or incompatible clock epochs remain `Unknown` with the supplied reason; lifecycle phase alone cannot establish zero. |

Formatting requirements:

- A measured numeric zero displays `0 core·s` / `0 s`. Null, unavailable and omitted measurements display `Unknown`, with the appropriate explanation. Truthiness must not determine availability.
- Display nonzero values with up to three fractional digits and readable units; disclose the exact supplied value/unit. A positive value smaller than the display resolution uses `<0.001 core·s` or `<0.001 s`, with an accessible reading such as `less than 0.001 core-seconds`; it must not become zero. Preserve source precision in the typed data and exact disclosure. Convert milliseconds to seconds only when the shared contract declares milliseconds.
- Keep units with their value where possible, while allowing labels, reasons and IDs to wrap. Unknown is text, not a dash, blank or empty bar. Use existing locale-aware formatting and whole English fallback messages; no scattered concatenated reason strings.
- CPU, run and queue availability are independent. A known CPU total does not manufacture a missing duration or wait; missing queue evidence does not erase a known CPU value. Render authoritative quality/reason fields from the shared contract, not inference from exit status or field presence.

### Scope, completeness and overlap

Always show `Scope: Owned command + waited descendants` beside the measurement block, with `Complete for recorded scope`, `Partial` or `Unknown` as supplied. The literal scope identifier **`native_waited_descendants`** belongs in Accounting details. The short scope help is `Includes descendants represented in native termination accounting. Detached or unobserved descendants are outside this scope.` Only use this label when that is the reported scope; never relabel a root-only or sampled subset as the same complete total.

`Complete for recorded scope` means the reported termination accounting for that scope is complete. It is not a statement about an arbitrary process tree, live process liveness or all process-group peers. No process-tree total is claimed in this release. Unrelated foreground/pipeline members do not belong to the owned execution merely because they share its group.

For an incomplete number, place **`Partial — {mapped reason}` in the same value block**, readable before any disclosure. Example copy, usable only when backed by that reason: `CPU used 2.3 core·s · Partial — Descendant coverage is incomplete.` If no useful quantity survived an interruption, use `CPU used Unknown` and the recorded reason; do not invent a lower bound. A summary-level Partial reason also stays visible, and each affected field is identified. Do not paint every valid field complete when the contract only supplies overall partial quality. Unknown availability, partial coverage, attribution basis and lookup error are separate concepts.

Canonical root accounting is the sole additive total for an execution root. A verified nested inclusive observation remains associated with its own job and visibly says **`Included in accounting root {id}; not additive`**. Preserve the selected nested job's ID and outcome; expose the root ID in the adjacent explanation and details. Opening another route or adding root navigation is unnecessary. Never add nested totals, or sampled values plus a terminal inclusive total. If lineage is unverified, display the supplied uncertain attribution/Partial or Unknown reason; do not infer ownership from a process group, ID resemblance, argv or timestamps. If the backend's attribution is an estimate, carry its explicit Estimated qualification; do not promote it to a native proven total.

### Accessible technical disclosure

Use native `details` / `summary` named **`Accounting details`**, styled like RecordedTime with existing semantic focus-ring and text tokens. The three values, scope, Partial reasons and nested non-additive explanation remain outside this disclosure. Inside, provide labeled, wrapping fields from the validated projection:

- Exact CPU total, user CPU and system CPU with their declared units, plus exact run/queue values and separate clock/basis descriptions. Missing components remain Unknown even if a separately valid total exists.
- Accounting scope (`native_waited_descendants` when reported), attribution basis, completeness and mapped reason. A raw supported reason code may accompany its readable explanation.
- Owned-child process identity: PID, start token and boot identity as supplied; distinguish observer identity if supplied. PID alone does not establish attribution. Do not turn start tokens into wall dates or lose integer/string precision.
- Accounting root job ID and verified root/nested relationship. Raw bounded report identity may be shown if included by the shared projection; it is not a command or permission token.
- Recorded accounting time when available, **`Summary received by desktop`** for a successful receipt, and the latest lookup time separately when relevant. Reuse RecordedTime for exact instants; timestamps are not duration inputs.

Raw identity means only the bounded, approved local measurement fields. Never dump an IPC object or exception. Preserve redaction of command text/argv, cwd/private paths, environment, secrets, socket endpoints, tokens and unapproved extra properties in visible text, tooltips, accessible names and errors. This task adds no telemetry or export. Existing snapshot payload and its redaction contract remain intact.

## State and interaction table

Accounting quality and retrieval freshness are two axes. A complete persisted terminal record stays complete for its recorded scope while its lookup is stale; a newly received partial record is still Partial. A successful health check does not establish a fresh summary. A new daemon process window affects host/daemon readings independently of historical job measurements.

Copy below is the presentation contract; map it to authoritative shared result/reason types. Do not invent wire enums or classify legacy/interrupted data from age or phase alone.

| Condition | Visible measurements and feedback | Read / retention behavior |
| --- | --- | --- |
| No selection | Existing `Select a job to view recorded details.` | No summary request without a valid selected job ID. |
| Initial selected-job read, no matching cached summary | Three `Unknown` values with `Loading job measurements…`; measurement region is busy. | Never display another job's values under this ID. Keep available job detail independent. |
| Refresh of a matching accepted summary | Retain values/quality with `Refreshing job measurements…`; busy only for this region. | No zero reset or flicker to another ID. Preserve focus and disclosure state for the same selection. |
| Queued/running, terminal accounting not yet recorded | CPU/run `Unknown · Waiting for termination accounting.` Queue wait may be shown independently only if supplied as a valid recorded interval. | No live tree sampling or inferred growing total. Availability is not a job failure. |
| Valid terminal report, complete for stated scope | Values, scope and `Complete for recorded scope`. | Exit 0, exit 17 or signal outcome is displayed independently. None changes accounting quality by itself. |
| Partial, or interrupted report with some valid data | Known affected values carry `Partial — {reason}` immediately beside them; unavailable fields remain `Unknown`. | Never fill a missing interval from wall-clock lifecycle timestamps. Interrupted measurements cannot become complete through refresh. |
| Legacy / no recorded measurement | `Unknown · No job measurements recorded.` Use `Legacy measurement unavailable` only for an explicit legacy reason. | No retroactive zero; a completed lifecycle record does not prove measured execution. |
| Native measurement unavailable | `Unknown` with the normalized measurement reason, e.g. `Native CPU accounting unavailable`. | Keep separately valid run/queue values and outcome. This is distinct from transport failure. |
| Unsupported daemon | `Unknown · Job measurements are not supported by this daemon.` | Keep health, Recent and detail usable. Stop repetitive unsupported probes for this connection; allow explicit Refresh status/reconnect/reopen to reprobe through the existing controller. |
| Malformed / mismatched / conflicting response | Existing `Invalid daemon response. The response was not used.` in this section. No cache: Unknown. Matching cache: retain it under `Last recorded measurements` and `Stale · showing last recorded data`. | Reject the new response; no raw payload/error output, automatic incompatible-response retry loop or overwrite. Existing explicit retry behavior applies. |
| Unavailable / uncertain transport | `Job measurements unavailable` plus the existing normalized connection/deadline message. No cache: Unknown. | Disconnect, hidden window, or retired request | Retain accepted matching values and completeness; label retrieval stale/paused using existing messaging. | Retire the request generation; no new hidden-window polling, new timer or presumed cancellation of a native read. |
| Daemon restart | Retain old matching summary as last recorded until a new accepted lookup; then replace freshness only. | Re-read by job ID. Never reset durable job CPU to zero with the host daemon counter. Old-epoch replies cannot overwrite new-epoch results. Missing termination evidence remains Partial/Unknown. |
| Not found after earlier match | `No matching job measurements.` Keep prior matching values separately as `Last recorded measurements`, stale, with latest lookup time. | Distinguish confirmed absence in this lookup from prior accepted evidence. Absence proves neither expiry nor nonexecution. |
| Not found without earlier match / outside Recent | No matching summary: Unknown with absence explanation. The 90-day metadata policy adds no TTL input or countdown. |
| Identical duplicate receipt | Same values, quality and scope; a valid new receipt may update its received time. | JSON property order is irrelevant. No duplicated rows, cumulative addition, repeated announcement or extra write. A conflicting immutable report follows the invalid-response row. |

## Selection, refresh and interface handoff

1. Route the additive authenticated `meter.summary` read through a fixed registered Tauri operation, following the `meter_snapshot`/`job_by_id` pattern, and a typed client method accepting only the selected job ID. Suggested mirror names are `meter_summary` and `meterSummary(jobId)`; backend-desktop reconciles exact names with the shared contract. Do not add a generic IPC/SQL/execution proxy, PID picker or frontend-computed accounting schema.
2. Use the shared schema/units/quality/reason definitions. Validate at the production bridge and frontend boundary. The UI needs the matching job ID, root relationship, nullable measurements, units/clocks, identity, basis, scope, completeness/reasons and receipt metadata described above. This is a semantic handoff; backend-native owns serialized field names and validity rules.
3. Bind each read to selected job ID, selection generation, controller generation and connection epoch. On A → B, clear the visible A summary immediately. Ignore late A success **and failure** under B, including A → B → A responses from an earlier generation. A reply claiming another job ID is invalid even if its numbers look plausible.
4. Extend the existing single refresh owner and bounded native serialization. A measurement failure stays local to that section, and a detail failure does not discard an independently validated matching summary. Do not introduce request-per-render behavior, overlapping socket reads, another polling clock or an unbounded per-job cache. Retaining the current selection's last valid summary is sufficient.
5. Retire reads on hide, connection change, selection change and unmount using existing lifecycle rules. Explicit retry/reopen performs metadata reads only. Completed measurement receipts may be old history yet remain valid measurements; present lookup freshness separately. Do not store new receipt times on failed reads.
6. Preserve current protocol-1 operations and the host `meter.snapshot` contract. Summary failure cannot change command execution, fail-open, wait/signal handling, exit semantics or desktop hide/quit behavior. The production SQLite → authenticated daemon → fixed Tauri bridge → typed client path must be checked by the implementation owners; fixture agreement alone does not establish that path.

## User evidence and retention decision

No field tests, retention experiments, activation counts, churn measurements or cost/revenue observations were supplied or collected here. Persona needs, faster comprehension and fewer navigation steps beyond the structural comparison are hypotheses.

**Ship clear inline information.** The proposed recurring next-open `Review CPU usage` nag is a retention hypothesis. It adds an interruption to a utility whose immediate goal is explaining one command, and may prompt opens without helping diagnosis. Effects on conversion, repeat use, churn and task success/time are unknown. This release adds no recurring prompt, forced review, artificial urgency, quit friction or instrumentation. Existing refresh/hide/quit semantics remain clear.

Optional later study, **proposed only and not run**: recruit three intended users covering first use, repeat diagnosis and keyboard operation. Give each find-job, CPU/run/queue interpretation, partial-scope identification and exit-17/disconnected-recovery tasks. Counterbalance inline and collapsed prototypes; record unassisted task success, interpretation errors, actions, elapsed task time and attempted reruns. Prefer inline if all understand scope/quality and recovery without rerunning and its median time is no worse; revise copy on observed confusion. A three-person qualitative session cannot establish population retention or conversion. It adds no mission acceptance gate.

A later separately authorized retention study could compare an inline cue with an optional recurring prompt using consented aggregate exposure/read/retry counts and voluntary diaries. Predefine eligible first-summary conversion, 7/30-day repeat use, churn, task success/time and support cost; a spike in opens alone would not justify the nag. No such study, instrumentation, participant outreach or distribution is part of this task.
