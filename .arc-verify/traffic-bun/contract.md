## Problem and source boundary

Direct, one-shot local `bun test` must share the existing FIFO, TEST window, CPU and memory reservations with `cargo test`. The CLI must still spawn the native child exactly once. Protocol 1 has strict enum and object decoders; changing their vocabulary or response shape without a boundary can break an old peer.

The inspected HEAD is `16772fe2aa350413225f3fb2bb9227d14ae5a6c4`, tree `1834e0cccb50a12fea299618f9a360f4ca10e03f`. Source facts:

- `crates/arc-detector/src/argv.rs` classifies native argv without a shell; `rules.rs` currently treats `bun test` as `UNRESOLVED_COMMAND`. `types.rs` has a closed `Reason` enum and validates whole classification combinations. `arc-detector/src/lib.rs` also uses the rules for the public shell-classification operation.
- `crates/arc-cli/src/exec.rs` owns the single `Command::spawn`; `exec/traffic.rs` admits only the existing Cargo reasons, probes `traffic.capabilities`, handles queued notices and retries, and reuses the lineage witness. `exec/preparation.rs` owns legacy lifecycle fallback and its existing error behavior. `exec/transport.rs` opens a new connection for each attempt and maps `UNSUPPORTED_CAPABILITY` to its unsupported result for the existing Traffic capability probe and `STATUS_V2`; Bun needs operation-specific handling that preserves prior enqueue uncertainty.

## Wire decision

| Option | Implementation and operation | Compatibility and future cost |
| --- | --- | --- |
| Reuse an existing reason such as `CARGO_TEST` or `COMPOUND_LOCAL` for Bun everywhere | Fewer types and no capability probe. The existing old daemon might make a scheduling decision on the substitute. | The first reason falsely says Cargo; the second falsely says a direct command is a compound. Treating compound classifications as admissible can also change unresolved-command behavior. It gives status readers no truthful tool identity and makes later separation harder. Reject. |
| Probe, then send Bun through existing `traffic.job` | Smallest change to the current operation, but the probe and enqueue have separate connections. | Reject: replacing the daemon after a successful probe exposes `BUN_TEST` to the old daemon's strict decoder, which returns a rejection rather than the required fallback. Keeping a probe result in memory does not bind the peer. Binding a persistent session would change transport/reconnect behavior and still need uncertain-commit recovery. |
| **Add a separately probed Bun capability and a Bun-specific job operation** | Add a protocol-1 probe and an operation whose name gates typed Bun decoding and Bun control requests, plus a local native-argv reason and legacy response projection. Reuse the durable queue, permits, worker, witness, status and lifecycle. No new service or dependency. | An old daemon rejects the unknown job operation before decoding the new reason, even after a successful probe and replacement. Bun control requests cannot accidentally be acknowledged by an old daemon using a different database. The client must distinguish a definitive unsupported reply from one following a possibly committed attempt. The new reason must be projected at every legacy response; stored classifications create the downgrade risk below. Select. |

The costs are qualitative. No runtime, implementation-hour or monetary comparison was measured.

### Selected protocol

1. Add an internal `BUN_TEST` reason, consistent only with `TEST`, `HOST_LOCAL`, `NONE`. Restrict its recognition to direct native argv, not the shared shell parser. Leave `job.classify` protocol-1 behavior for Bun and Bun-containing shell expressions at its existing conservative result; `arcctl classify` is not evidence of admission. A later richer classification operation would require its own opt-in contract.
2. Add a null-payload protocol-1 probe, operation `traffic.bun.capabilities`, whose exact successful result is `{ "capability": "traffic.bun.v1" }`. This capability promises the existing Traffic operations and the Bun job operation defined below. Do not add a field or value to the existing `traffic.capabilities` result, alter `traffic.v1`, or change protocol version 1. Probe replies must pass the existing authenticated endpoint, request-ID, version, status and strict-shape checks. Map a validated `UNSUPPORTED_CAPABILITY` response for this probe in `exec/transport.rs` without broadening error handling for other operations. The accepted daemon dispatch returns that error for an unknown operation. The probe is feature discovery only: it does not bind a subsequent connection to that daemon or establish an enqueue outcome.
3. After the probe succeeds, send operation `traffic.bun.job` with the existing strict `JobRequest::Enqueue` payload, the same job ID, observer and lineage fields, and classification `TEST/HOST_LOCAL/BUN_TEST/NONE`. The new daemon must select this operation before decoding its payload, accept only that classification on its `ENQUEUE`, authenticate the peer and use the same bounded worker and atomic admission path as Cargo. Reject `BUN_TEST` `ENQUEUE` on the legacy `traffic.job` operation, so it cannot become an accidental alternate wire contract. Use `traffic.bun.job` for every Bun re-enqueue, including inherited-lineage wait cycles, and for that job's `POLL`, `ATTACH`, `COMPLETE`, `CANCEL` and `FALLBACK` requests; these use the same validated request/result shapes and worker semantics as their existing equivalents. Carry the chosen route through the CLI's mode and helper calls, including witness cancellation and spawn-failure paths. Reject unsupported actions and combinations. For status, retain the old `traffic.job` `STATUS` and `STATUS_V2` interface. Cargo keeps its current path. The probe and new operation are never sent by an old client. A new daemon must never return `UNSUPPORTED_CAPABILITY` after dispatching a `traffic.bun.job` request to the worker; reserve that error for an unimplemented operation before any worker admission, and return the existing appropriate error for malformed input or handler failure.
4. Every old lifecycle response that can include a Bun `JobSnapshot` must project its classification to the valid old tuple `UNKNOWN/UNKNOWN/UNRESOLVED_COMMAND/OBSERVE` before serialization. Do this to the response copy, not the stored row used for policy, duplicate detection or recovery. The projection includes `job.status` by ID and any `job.start`/`job.complete` snapshot response; audit every path returning a snapshot. Reject a new Bun reason in legacy lifecycle registration rather than sending it to an old daemon. Recent summaries contain a lifecycle reason, not a classification. Existing `traffic.job` status has no classification and remains byte-shape compatible.
5. A new client against a pre-Bun daemon uses the legacy lifecycle path with the old unresolved tuple after a valid matching unsupported Bun probe. A Phase 1 old daemon advertising `traffic.v1` is still pre-Bun until it advertises the separate capability; a pre-Traffic daemon has the same fallback. If the daemon changes after a successful probe but before the first enqueue, the old daemon receives the new operation and an untyped JSON payload containing `BUN_TEST`, but must reject the unknown operation before its strict `Reason` decoder runs. A validated matching unsupported response is a no-commit proof only for that attempt, not for earlier attempts. With no earlier potentially committed attempt, discard the unused witness, register the old unresolved tuple and launch once without a Traffic reservation. Never put `BUN_TEST` in a legacy `job.start` or a `traffic.job` `ENQUEUE`; legacy `start_until` compares the returned classification with the registered one. This is observe/bypass, not proof of scheduled admission.
6. Track enqueue uncertainty across all transport attempts and wait cycles for the same logical job, not just the most recent connection. Before classifying a matching unsupported enqueue reply, consult whether an earlier attempt could have reached admission: a write followed by a lost or incomplete reply, a timed-out worker/`DB_BUSY`, or a previously confirmed queued/granted state makes the job potentially committed. Connect failures before any request bytes were sent do not. The current complete unsupported reply itself is proof that its own unknown operation was not dispatched; do not count its successfully sent bytes as prior uncertainty. Only if there is no earlier possible commit may it return `Unsupported` and take the legacy fallback in step 5. Otherwise return the existing witness-backed `Mode::Uncertain`, retain the same job ID, and take the existing bounded fail-open launch and metadata-only reconciliation path. Do not discard the witness, make a new job ID, register a separate legacy job, or infer that the earlier queue or permit is absent. An unsupported re-enqueue or poll after an acknowledged queue is likewise uncertain; a `POLL` `NOT_FOUND` from a replacement peer cannot erase a previously acknowledged queue. Cancellation still records unspawned evidence and never launches a child. On recovery, remove an unreserved queue position or retain/reconcile a possibly granted reservation until the existing safe release conditions are met. These guarantees do not promise global scheduling during an outage.
   - An old peer's rejection of Bun control requests is not a cleanup acknowledgement. In particular, do not send uncertain Bun cleanup through legacy `traffic.job`: on another database it could create an unrelated tombstone and return `ABANDONED`, which `exec.rs` currently treats as permission to discard the witness. A successful probe on a separate connection does not prove database continuity either. Retain the witness whenever the original store and cleanup cannot be established; use recovery against the original database and its existing identity, claim and safety checks. A small conservative implementation can suppress acknowledgement-based witness deletion for the rest of an invocation after this ambiguous replacement, leaving the original daemon's recovery to consume verified evidence; if recovery cannot prove safety, a stale witness may remain. If no proof is available, leave recovery unconfirmed rather than discard evidence or invent an outcome. Reconciliation tests must distinguish a new daemon reopened on the original database from a replacement using a different database.
7. A timeout or unreachable daemon before enqueue follows the existing bounded unavailable/uncertain fail-open path. A malformed response, mismatched ID/version, protocol incompatibility or authenticated rejection follows the existing error path and is not recast as unsupported. If an earlier enqueue might have committed, preserve and record the unspawned witness on that non-spawn error path until cleanup is confirmed. Lost enqueue/grant/attach/complete acknowledgements use the same job ID and existing witness and reconciliation; never spawn from a retry. Queued cancellation and pre-spawn cancellation remain non-spawning; preserve current witness and permit-release rules.

An old client using `traffic.job` can obtain the existing queued, running and completed Traffic states for a Bun job by ID, including wait and outcome where those fields exist. An old lifecycle client receives a decodable last-known lifecycle state and the conservative unresolved classification; it must not be told that Bun is Cargo. It may lack a queue label because the old lifecycle phase vocabulary has none. The new CLI uses the existing `STATUS_V2` path and presents queued, starting, running, completed, cancelled or unknown according to the returned state; it must not expose lineage context or command data. Do not expand either old status result with a Bun field. Preserve the current legacy `STATUS` versus `STATUS_V2` handling for newer uncertainty states.

**Database downgrade risk:** the existing generic codec persists `classification_reason`, and the old daemon's closed enum cannot decode a stored `BUN_TEST`. This decision needs no new SQL migration, but it does not establish that an old daemon can reopen a database after a new daemon has stored Bun rows. Protocol peer compatibility on an old daemon with its compatible database is required below; rollback of a newly written database is a separate unresolved compatibility risk for the Chief. If same-database downgrade must be supported, the codec, admission and active-accounting changes in `crates/arc-storage/src/jobs/codec.rs` and `crates/arc-storage/src/jobs/traffic/{admission,store}.rs`, and any forward migration/registry, are outside task 2's saved ownership and require coordination. Do not hide the issue by rewriting an old migration or presenting a different reason as the real tool.

## Eligibility and shared policy

- Admit only an actual direct argv whose program token is `bun` and whose next token is `test`, with bounded, confidently resolved one-shot options and patterns. Preserve the existing detector's token, input and work budgets. The test executable still receives the original OS argument bytes unchanged.
- Admit ordinary one-shot forms such as `bun test`, test-file patterns and recognized one-shot options with valid values. Parse options according to their arity and the actual supported Bun semantics; distinguish flags from values and substrings. A value such as `--test-name-pattern=watch` or a filename containing `watch` is not itself a watch request. Unknown, ambiguous, non-UTF-8 or over-budget forms remain observe/bypass rather than guessed admission.
- `bun test --watch`, `bun test --hot`, watch/hot assignments or ambiguous forms that could enable those modes bypass without waiting or reserving. Include boundary cases around separated values, `=`, a `--` token, short options and flag-looking patterns; where the supported Bun behavior is not established, bypass. `bun run test`, shell wrappers, scripts, compound commands, alternate executable spellings that the detector cannot positively identify, and remote/SSH commands retain conservative bypass. A waiting TEST job must not block these bypassed commands.
- Once admitted, Bun and Cargo are the same TEST class: identical configured TEST reservation, one count per root permit, global CPU millicores and memory-byte totals, and existing FIFO/lineage accounting. Defaults at this snapshot are TEST window 1, 1,000 millicores and 1 GiB; global budget 2,000 millicores and 4 GiB. These are reservations, not OS-enforced resource ceilings.
- A window-only test does not prove the resource budget. With TEST window at least 2, run separate deterministic policy/storage cases in which a live Cargo TEST reservation makes a Bun TEST wait for CPU while memory is ample, and where memory is decisive while CPU is ample; reverse the tool order as well. Assert `CPU_BUDGET` or `MEMORY_BUDGET`, unchanged active accounting while waiting, and admission only after release. Also test overflow and existing invalid-policy behavior.
