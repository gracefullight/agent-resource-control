## Meaning of status, evidence and cycle

| Status | Assessment | Interpretation |
| --- | --- | --- |
| Complete | Complete | The stated requirement behavior or catalog decision has affirmative focused execution evidence for the delivered supported implementation. This is not a final-gate, entire-phase, Windows or full-product completion claim. |
| Partial | Partial | Concrete execution/source evidence covers a named subset; the remaining SRS scope is stated. |
| Pending | Unverified | Implementation/measurement may exist, but the required current execution, calibration or external observation is not established. |
| Pending | Outstanding | The full obligation has no delivered acceptance in this mission and remains future scope. This does not assert that all related source is absent repository-wide. |
| Blocked | Blocked | A required prerequisite prevents assigned acceptance. No primary row is placed here merely because broader work is outside this slice. |

The Assessment column separates **unverified** from **outstanding** while preserving task-13's exact status vocabulary. Tables below report both forms. All row Cycle values identify this current evidence assessment. Historical cycle receipts are retained separately in the provenance ledger with their own dates, heads and verification boundaries; they never silently certify current source.

Evidence-cell paths follow the validator's **repository-root-relative** convention. `#/...` selects a real JSON receipt field/case; code selectors are exact source text. Source-column links are relative to this document and retain the SRS section and declaration line. A link to a specification or a raw-log hash alone is not an executed result. Complete rows link an actual affirmative case or an argv/exit-0 command receipt. Failed, null, unexecuted and specification-only selectors are not completion proof.

Supported scope is direct local Cargo build/test/clippy/fmt and supported one-shot Bun test, with current-client capability negotiation. Pressure in deterministic Critical scenarios is explicitly injected through the production daemon/Meter seam; separate actual SystemSource observations show macOS Normal sampling. ## Primary phase rule

Primary phases follow [SRS §22](ARC_SRS_2026-11-06.md#22-구현-로드맵-및-단계별-definition-of-done), not priority P0/P1/P2. Phase 0 owns core/IPC/locality foundations; Phase 1 owns basic Meter/Traffic and this Governor slice; Phase 2 owns full vendor/tool-family extension; Phase 3 owns Sweeper, ownership/deletion and telemetry consent; Phase 4 owns adaptation, detailed UX/accessibility/localization and performance polish; Phase 5 owns stable cross-platform release/packaging and final platform budgets.

A cross-phase obligation has one primary owner for counting. Examples: DET-003 is Phase 2 because its complete nine-family catalog exceeds the Phase 1 direct-tool subset; TRF-011/POL-005 are Phase 4 despite the Phase 1 Critical hold; NFR-018 and NFR-021 are Phase 3 because their complete scope includes Sweeper/GC; AT-GUI-02 is Phase 4 because its full Settings catalog includes learning; NFR-017 and G-08 are Phase 5 final-platform obligations. Cross-reference appearances never add another primary row or completion.
